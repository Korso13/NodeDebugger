NodeDebugger by Tim Korso

Что такое NodeDebugger?

NodeDebugger - дебаг-утилита для W4 проектов, которая также служит своеобразным редактором для уровней и настроек

Включает следующий функционал:

  • Редактирование трансформов нод и их наследников
  • Редактирование свойств мешей, таких как RO и настройки материала
  • Дебагинг спайнов (выбор скинов, проигрывание анимаций, изменение свойств материалов в слотах)
  • Управление камерой (в том числе с клавиатуры)
  • Управление скоростью геймплея (Timescale)
  • Управление переменными большинства базовых С++ и W4 типов
  • Управление значениями из файлов settings.json + экспорт изменённых настроек в (единый) json
  • Вывод дебажных вызовов в виде кнопок (как UI так и на клавиатуре)
  • Редактор твинов с экспортом в json
  • Редактор файлов границ (для классов Border и StaticIntersectBorder) с рисованием через клики по карте (с нажатым Ctrl)
  • Редактор путей для класса Pathfinder с добавлением Path Node через клики по карте (с нажатым Ctrl) и рисованием путей через соединение путевых нод левой кнопкой мыши
  • Инструментарий для инстанциирования мешей, а также объектов произвольных классов с последующей возможностью редактирования их свойств и экспортом в файл json (для последующей подгрузки как файл с содержимым уровня)
  • Редактор Spotlight нод
  • UI для вывода дебаг-сообщений консоли (например на моб устройствах)

Версия

  • Текущая версия 5.0

Установка и Настройка NodeDebugger

Для установки необходимо закинуть папку nodeDebugger в папку sources/common проекта, а также подкинуть дополнительные файлы из extra sources в папки js и sources/settings. В папке sdk fixes лежат фиксы для движка (без них например забаговано изменение контейнеров через UI).

В начале файла NodeDebugger.h можно подсмотреть большинство макросов для быстрого вызова функционала NodeDebugger (регистрация нод и спайнов в дебагере, добавление дебаг команд, вывод переменных в UI дебагера и т.д.), а также имеющихся клавиатурных команд.

В файле common/nodeDebugger/ND_Defines.h также можно отключить некоторые вкладки закомментировав макросы

  • NDSPINES - спайны
  • NDVARIABLES - переменные
  • NDBORDERS - редактор границ
  • NDPATHDRAWER - редактор путей (требует Pathfinder.h!)
  • NDSPOTLIGHTS - редактор SpotLight
  • NDCONSOLE - вкладка с консолью
    и отредактировать некоторые настройки:
  • JSON_FLOAT_ACCURACY - точность чисел с плавающей точкой при экспорте в json
  • IMG_STARTSIZE - размер окна дебагера по дефолту
  • IMG_FONTSIZE - размер шрифта дебагера
  • IMG_FLOATFORMAT - точность чисел с плавающей точкой на вкладке Variables
  • IMG_VECFORMAT - точность значений x,y,z для векторов на вкладке Variables

Для инстанциирования произвольных классов через Spawner потребуется дополнительная настройка из кода (о ней ниже).

Использование Spawner

Вкладка Spawner позволяет создавать меши и объекты классов, настраивать уже созданные и экспортировать их в файл mapObjects.json. Этот файл (расположенный в resources/config) впоследствии Spawner будет подгружать и на его основе создавать и настраивать меши и прочие объекты. По сути это своеобразный редактор уровня для W4.

Создание мешей доступно из коробки. Для создания объектов произвольных классов потребуется настройка.

Для доступа к фабрике объектов используется макрос SPAWNER

Загрузка и выгрузка объектов из/в json

Добавляем

#include <common/nodeDebugger/spawner/SpawnerFactory.h>

Чтобы выгрузить созданные меши и объекты в json, перейдите на подвкладку Spawned Objects и нажмите кнопку Export All. Настоятельно советую не сохранять файл напрямую в resources/config, т.к. в большинстве случаев движок закэширует намертво старый файл и придётся зачищать кэш и пересобирать проект! Лучше выгрузить отдельно и потом перезаписать файл через Проводник или любой другой файловый менеджер.

Чтобы загрузить объекты из файла mapObjects.json достаточно вызвать SPAWNER.SpawnObjects();
Однако этот вызов должен идти строго после всех команд, связанных с регистрацией инстанциируемых классов (registerSpawnableClass() - об этом см. ниже)!

В общем и целом, интеграция ваших классов в Spawner состоит из 3+ шагов:

  1. Регистрация класса в Spawner фабрике с настройкой колбэка при создании объекта (как правило происходит в классе LevelGame)
  2. Регистрация корневой ноды класса + вывод переменных и дебаг методов в UI созданных объектов (делается в коде самого класса)
  3. (Делается 1 раз) Удалить ваше определение структуры MapObjectsData или перенести нужные поля в его определение в файле common/nodeDebugger/spawner/SpawnerStructs.h (подробнее см. ниже)
  4. (Опционально) Изменение структуры MapObjectsData, которая используется для импорта и экспорта настроек объектов на карте
  5. (Опционально) сериализация нужных вам (экспортируемых и/или выводимых в UI) enum и структур.

Первоначально, регистрация уже имеющихся классов у вас может занять несколько часов, но т.к. большинство классов кочуют из проекта в проект, временные расходы в последующих проектах будут минимальными.

Регистрация классов в Spawner

Для регистрации классов в Spawner требуется отнаследовать эти классы от класса Spawnable (common/nodeDebugger/spawner/Spawnable.h) или же написать обёрточный класс, который наследуется от Spawnable, инстанциирует его и вас класс (пример можно найти в common/nodeDebugger/spawner/SpawnerWrappers.h, туда же можно дописывать ваши обёртки).
Учтите, что конструктор Spawnable в обязательном порядке требует ссылку на MapObjectsData - структуру, которая хранит все настройки конкретного объекта из файла mapObjects.json!

Далее вашего наследника Spawnable нужно зарегистрировать в фабрике SPAWNER (увы, на данный момент это приходится делать в рантайме вместо compile time). Сделать это нужно до загрузки объектов из файла json ( SPAWNER.SpawnObjects() )!
Делается это через такой синтаксис:

SPAWNER.registerSpawnableClass<Ваш_Класс, Тип_Аргумента_Констурктора_1, Тип_Аргумента_Констурктора_2 ...>
	(
		CLASS2STR(Ваш_Класс),
		{ "Название аргумента 1 для UI", Аргумент_Констурктора_1},
		{ "Название аргумента 2 для UI", Аргумент_Констурктора_2 }
		...
	)

Все аргументы будут выведены на палетке с классами (подвкладка Class Palette) и будут доступны для редактирования с рядом оговорок:

  • Ноды будут отображены в виде селектора любой ноды (все наследники Node) из иерархии нод
  • sptr не поддерживаются, кроме sptr<Node>
  • Для отображения своих структур и enum требуется их сериализовать (макросы JSTRUCT_DEFINITION, SERIALIZE_ENUM и MAKE_SERIALIZED_ENUM_CLASS, о них отдельно будет сказано ниже)
  • Т.к. любые наследники Spawnable должны иметь в конструкторе ссылку на MapObjectsData, перед вызовом registerSpawnableClass следует создать эту структуру в локальном скоупе. Заполнив поля этой структуры вы также можете задать свои дефолтные значения этих полей, чтобы их не пришлось потом заполнять в UI дебагера, например дефолтное положение точек взаимодействия.

Формально, класс уже можно инстанциировать с вкладки Spawner-Class Palette - Открываете вкладку, раскрываете пункт с нужным вам классом, заполняете все нужные поля (значения аргументов конструктора), нажимаете кнопку Spawn. Новый объект будет создан, причём перед камерой в нулевом z (при условии что вы корректно настроили класс внутри - об этом будет инфа ниже).

Вызовы при создании объекта и пример регистрации класса

Spawner поддерживает ряд дополнительных настроек, чтобы сделать его использование и использование загруженных объектов более удобным.
registerSpawnableClass возвращает ссылку на структуру с настройками создания объекта фабрикой, у которой есть ряд полезных функций:

  • setOnSpawnCallback() принимает лямбду формата [this](sptr<Spawnable> newEntity), которая вызывается сразу после создания объекта и принимает аргументом указатель на этот объект (который можно кастить до вашего класса через cast_sptr<Ваш_Класс>(newEntity)). Позволяет сразу добавлять новый объект в нужные контейнеры, регистрировать на апдейты, вызывать отложенную инициализацию (если такая есть). Этот метод зовётся как при создании объекта из вкладки дебагера, так и при загрузке объекта фабрикой Spawner из файла json!
  • setOnDeleteCallback() принимает лямбду формата [this](sptr<Spawnable> newEntity), которая вызывается при удалении созданного объекта из списка созданных объектов (подвкладка Spawned Objects). Позволяет вычистить объект из всех контейнеров и переменных, где лежат указатель на него. Если написать лямбду корректно, удаление из Spawned Objects будет вызывать деструктор объекта.
  • setObjNameList() принимает вектор строк и выводит его в виде выпадающего списка в верху UI создания объекта класса в Class Palette. Выбранный пункт из этого списка автоматически будет записан в поле objName аргумента-структуры MapObjectsData. Например, передав в setObjNameList список ваших спайнов из spineContainerSettings.json и используя поле objName в конструкторе Enemy как название создаваемого спайна, можно упростить выбор типа создаваемого Enemy.

Все указанные выше методы, также как и registerSpawnableClass возвращают ссылку на структуру с настройками фабрики класса, что позволяет делать последовательные вызовы этих методов через оператор .. Таким образом все вызовы для одного класса сворачиваются в читаемую структуру кода (на примере BonusItemNoSprite):

	SPAWNER.registerSpawnableClass<BonusItemNoSprite, sptr<Node>, MapObjectsData&> 
		(
			CLASS2STR(BonusItemNoSprite),
			{ "Parent Node", m_view },
			{ "Spawn Data", spawnBonusData }
		).
		setObjNameList({"loot_armor_angelic", "loot_armor_nephrite", "loot_champion_armor"}).
		setOnSpawnCallback([this](sptr<Spawnable> newEntity)
			{
				sptr<BonusItemNoSprite> bonus = cast_sptr<BonusItemNoSprite>(newEntity);
				auto& obj = newEntity->getMapObjectsData();
				bonus->init();
				if (!bonus->isSpawned)
				{
					bonus->setWorldPos(obj.pos);
				}
				m_playerController->setItemClickCBs(bonus);

				m_levelItems.push_back(bonus);
				m_updateList.push_back(bonus);
			}
		).
		setOnDeleteCallback([this](sptr<Spawnable> newEntity) 
			{
				sptr<LevelItem> item = cast_sptr<LevelItem>(newEntity);
				auto& obj = newEntity->getMapObjectsData();
				//удаляем указатель на объект из вкладки Nodes
				NODEDEBUG->removeImGuiNode(item->getRoot()->getName());

				//Вычищаем указатели на объект из колбэков
				item->setClickCb([this]() {});
				item->setOnActivateCB([this](sptr<Player> playerRef) {});
				//Вычищаем указатели на объект из контейнеров
				std::erase_if(m_levelItems, [this, item](sptr<LevelItem> levelItem) 
					{return levelItem == item; });
				std::erase_if(m_updateList, [this, item](sptr<Updatable> updatable) 
					{return updatable == item; });
			});

В примере выше упомянут публичный флаг isSpawned из класса Spawnable. Он ставится в true при инстанциировании объекта с вкладки Class Palette и остаётся false при загрузке из файла json.

Настройка Spawnable классов

Для полноценной работы фабрики объектов в самих классах, которые мы наследуем от Spawnable крайне желательно вызвать один метод родительского класса (именно родительского!) - initSpawnable(), передав в него ноду, которая будет считаться корневой для объекта. Это позволит:

  1. Получить меню и гизмо трансформации ноды в настройках объекта (подвкладка Spawned Objects)
  2. Экспортировать и импортировать (кроме самых тяжёлых случаев плохого кода) расположение корневой ноды объекта в иерархии нод, а также её расположение в мировых координатах (происходит автоматически).
  3. В рантайме менять родителя корневой ноды объекта

initSpawnable() нужно вызывать в самом конце конструктора объекта или, если ваш объект инициализируется отложено, то в конце вашего метода инициализации объекта!

Т.к. initSpawnable() виртуальная функция, её удобно использовать для ещё одного слоя настройки Spawner - вывода полей объекта для редактирования в подвкладке Spawned Objects (но не забываем в любом случае вызывать родительский Spawnable::initSpawnable()!!).
Для вывода полей и прочего дебагинга отдельных объектов класса существуют две функции:

  1. addSpawnableSetting() принимает структуру типа SpawnSetting(о ней ниже) и выводит редактируемую переменную в окно объекта класса в Spawned Objects
  2. addSpawnableBtn() принимает строку (название) и лямбду (или ссылку на функцию через std::bind) и создаёт кнопку, вызывающую указанную логику, в окне объекта класса в Spawned Objects

Конструктор SpawnSetting принимает :

  1. std::string - название переменной, которое будет отображаться в UI
  2. Саму переменную (базовые и движковые типы, контейнеры с ними, сериализованные enum (багованы), enum class и структуры, sptr<Node>). Поддерживается как rvalue (&&) так и lvalue ссылки(&), однако с последним есть один нюанс - при изменении переменной через UI переменная по ссылке изменится, но при изменении переменной в самом коде, переменная в UI не обновится.
  3. Опциональный колбэк, вызываемый при изменении переменной через UI. Принимает лямбду формата [this](ваш_тип_переменной& var){}(для переменных по ссылке) или [this](ваш_тип_переменной var){}(для остальных).

Поскольку addSpawnableSetting() позволяет редактировать любые переменные, в том числе отдельные поля структур, для отдельных объектов, имеет смысл вывести через этот метод нужные вам поляMapObjectsData. Вы можете дополнить нужными вам полями содержимое MapObjectsData, затем задать нужные значения этих полей через UI отдельных объектов (например положения точек атаки для врагов) и экспортировать их в mapObjects.json (туда попадает содержимое структуры MapObjectsData, хранимой каждым Spawnable).

При загрузке объекта из json, он получит в свой конструктор ссылку на MapObjectsData со своими данными и сможет использовать значения её полей для настройки объекта. Доступ к своему MapObjectsData любой наследник Spawnable может получить через метод getMapObjectsData()

Пара нюансов:

  • Изменение значений массивов (независимо от того, как их передали) не вызывает колбэков (3ий аргумент) и при экспорте в JSON будут необновлённые значения! Это бага движка, фикс для неё лежит в папке sdk fixes.
  • Если вы передаёте переменную как rvalue (movable копия), обязательно пропишите колбэк, иначе у вас ничего не будет меняться в вашем объекте или изменённое значение не попадёт в экспорт MapObjectsData (впрочем его поля по-хорошему должны передаваться по lvalue)!
  • Сеттинг типа sptr<Node> будет отображаться как меню трансформа + гизмо + будет подменю смены родительской ноды. В экспорт автоматом пишется родительская нода только для корневой ноды объекта, поэтому если вам нужно сохранять адрес какой-то вторичной ноды, создайте в MapObjectsData дополнительное std::string поле, и через колбэк к сеттингу пишите туда нужный адрес (функции для парсинга адреса см в разделе “Прочие функции Spawner”).

Сериализация struct и enum

Как уже писалось выше, для экспорта любого enum или struct в json или для вывода его в UI дебагера требуется для начала их сериализовать. Сразу оговорюсь, что в движке забагован вывод обычных enum (c enum class всё в порядке) в UI, по возможности избегайте их использования.

Для сериализации структур их необходимо объявить через макрос JSTRUCT_DEFINITION. Делать это желательно в файле common/nodeDebugger/spawner/SpawnerStructs.h (так он точно будет известен фабрике и всем наследникам Spawnable). Синтаксис у этого макроса специфичный:

JSTRUCT_DEFINITION(MapMeshData,
	((std::string, meshName, ""))
	((std::string, material, "sprite"))
	((std::string, node, ""))
	((int32_t, renderOrder, 1))
	((bool, useWorldPos, true))
	((vec3, position_world, vec3::zero))
	((vec3, position_local, vec3::zero))
	((vec3, scale_local, vec3::one))
	((vec3, rotation_local, vec3::zero))
);

Первым аргументом передаётся название вашей структуры (в примере выше MapMeshData), затем после запятой указывается список кортежей. Каждая запись отделена через двойные скобки, запятые между кортежами не используются!!
Содержимое двойных скобок задаётся следующим образом:
((тип_данных, название_поля, значение_поля_по-умолчанию))
Все три значения обязательны! Если у вас имеются поля типа struct или enum их тоже нужно сериализовать через JSTRUCT_DEFINITION!

В типе данных, названии поля и дефолтных значениях не должно быть запятых! Если вам нужно использовать map воспользуйтесь шаблонным псевдонимом settingMap<T> или settingUMap<T>(для unordered_map) - иначе вы получите ошибку компиляции из-за запятой в шаблоне!

Структуры объявленные через JSTRUCT_DEFINITION:

  • Автоматически поддерживают выгрузку в/из json.
  • Причём в файл json попадут только поля, значения которых отличается от значения по умолчанию
  • При загрузке из json движок не крашится, если не находит какого-то из объявленных полей, а просто инициализирует его дефолтным значением
  • Эти структуры можно выводить в UI дебагера (как через addSpawnableSetting(), так и через registerSpawnableClass())
  • Имеют дополнительное поле class, которое не выводится в UI Class Palette - class (требуется для корректной работы фабрики)

Для сериализации enum их нужно

  • либо объявить через макрос MAKE_SERIALIZED_ENUM_CLASS (это будет enum class)
  • либо сериализовать уже существующий enum макросом SERIALIZE_ENUM

Делать это всё желательно в файле common/nodeDebugger/spawner/SpawnerEnums.h (так он точно будет известен фабрике и всем наследникам Spawnable). Синтаксис у этих двух макросов одинаков, отличается только то, что у MAKE_SERIALIZED_ENUM_CLASS мы указываем название вашего нового enum class, а в SERIALIZE_ENUM - уже существующего.

Пример для MAKE_SERIALIZED_ENUM_CLASS:

MAKE_SERIALIZED_ENUM_CLASS(SPK_MATERIAL,
	(ADDALPHA)
	(ALPHA)
	(ADD)
);

Пример для SERIALIZE_ENUM:

SERIALIZE_ENUM(ViewDirection,
	(LEFT)
	(RIGHT)
);

О модификации MapObjectsData

Для работы Spawner использует активно структуру MapObjectsData, поэтому вам придётся удалить/перенести свою версию этой структуры в common/nodeDebugger/spawner/SpawnerStructs.h

В SpawnerStructs.h MapObjectsData определена через отдельный макрос MOD_DEFINITION, но синтаксис почти идентичен JSTRUCT_DEFINITION.
Этот макрос делает то же самое, но задаёт фиксированное название этой структуре.

Вы вольны менять содержимое структуры, объявленное в макросе MOD_DEFINITION, как вам удобно, но сохраните 2 важных поля:

  • objName
  • node
  • SPARK_Materials(или сначала закоментите обёрточный класс для Spark эммитеров из common/nodeDebugger/spawner/SpawnerWrappers.h)

Меню создания мешей (Mesh Spawner)

Позволяет размещать меши на уровне на любой существующей ноде, выгружать информацию о размещённых мешах в json и загружать меши из файла, сохраняя большинство настроек.
В верхней части подвкладки Mesh Spawner выбирается родительская нода.

Затем в Mesh Name выбирается меш из списка составленного по meshesContainerSettings.json (требуется наличие модифицированных классов Settings и SettingsContainer!!)

В Material указывается материал меша. На данный момент доступны не-шейдерные материалы. Если при внедрении nodeDebugger вы не забыли подкинуть изменённый MaterialContainer.h, то список материалов будет автоматически составляться из доступных нешейдерных материалов. В противном случае список будет фиксированным/зашитым через хардкод.

Также можно задать сразу RO, поворот и скейл меша. Положение указывать смысла нет т.к. меш будет создан по центру камеры на нулевом z.
После создания мешем можно управлять через подвкладку Spawned Objects.
На данный момент при экспорте меша сохраняется:

  • Тип материала (но не его настройки!)
  • Родительская нода (автоматически определяется при выгрузке)
  • RO
  • Положение в глобальных или локальных координатах (или-или)
  • локальный масштаб
  • локальный поворот

Получить меш после его загрузки (SPAWNER.SpawnObjects()) можно по методу SPAWNER.getMeshByName(), который принимает название меша (то, как он отображается в подвкладке Spawned Objects!!). При создании меша ему даётся либо название настройки из meshesContainerSettings, либо, если такой меш уже создан, название настройки + уникальный суффикс формата “_XXX” где XXX - порядковый номер.

Меню управления объектами и мешами (Spawned Objects)

В подвкладке Spawned Objects отображаются все объекты классов и меши созданные через Spawner или загруженные из mapObjects.json. Каждый объект/меш имеет уникальное имя и при раскрытии записи появится UI редактирования настроек объекта (если использовались addSpawnableSetting(), addSpawnableBtn или Spawnable::initSpawnable()) или меша.

Изменения внесённые через этот UI (при отсутствии ошибок в логике) будут успешно выгружаться в json и подгружаться назад (кроме оговорённых нюансов, типа настроек материала).

Меню созданных мешей, помимо стандартных опций для нод/мешей bp одноимённой вкладки дебагера, имеют ряд дополнительных:

  • Меню смены материала (в рантайме, попадёт в экспорт)
  • Ползунок Render Order (он дублируется ниже, но использовать лучше тот что выше; из-за недочёта в движке, при использовании нижнего ползунка RO в экспорт может не попасть корректное его значение)
  • Переключатель определяющий то, в каких координатах размещать меш при загрузке - локальных или глобальных
  • Селектор родительской ноды (в рантайме, попадёт в экспорт)

Прочие функции Spawner

  • std::string SPAWNER.getNodeHierarchyAddress(sptr<Node> node) - парсит положение ноды в иерархии в строку, которую можно экспортировать
  • sptr<Node> SPAWNER.findNodeByHierarchyAddress(std::string adress) - находит ноду в иерархии нод по переданному адресу формата название_ноды_0||название_ноды_1 ...
  • MAP_DATA - контейнер с mapObjectsData структурами всех объектов из mapObjects.json
  • MAP_MESH_DATA - контейнер с MapMeshData структурами всех мешей из mapObjects.json
